## 2. 熔断器缺口（真实 gap，需决策）

**发现**：`gateway_server.py` 的 `CircuitBreaker` 只**记录**状态（`record_failure`/`record_success` 仅在 `/api/generate` 的 ollama 分支调用），但 **`allow_request()` 从未被任何路由调用**——请求永远不会被 503 拦截。熔断器是"观测仪表盘"不是"断路器"。

- 证据：`grep allow_request` 只在类定义处出现；`record_failure` 只在 line 274。
- 影响：BLUEPRINT/README 将"熔断"列为网关能力（Phase A），若面试被问到"熔断怎么拦截请求"会塌。
- **决策（2026-08-16）：选 A，接线已落地** — `gateway_server.py` 在 `/api/generate`、`/api/chat/stream` 的 **ollama 分支**加 `allow_request()` gate：熔断打开后 ollama 请求 503 快速失败（不再等超时 502）；`record_success` 在拿到 200 时重置（含 stream），`record_failure` 在 `ClientError` 时计数。
  - **为何 gate 放分支不放入口**：熔断器跟踪的是 ollama 健康，若放入口会把故障扩散到 vllm 请求——本可正常服务的 vllm 流量被错误 503。熔断器保护谁就拦谁。
  - 验证：`test_circuit_breaker_state_opens_on_generate_failures` 断言第 N+1 次 ollama 请求返回 503 + "熔断"。
  - 边界：vllm 分支不记录也不拦截（vllm 健康由 vllm 自身承担，网关不拦）。

## 3. 401 观测缺口

**发现**：`auth_middleware` 是**最外层**中间件（后注册 = 外层），401 在进入 `metrics_middleware` 的 `call_next` 之前直接返回，因此 **401 不计入 `gateway_requests_total`**。拒绝流量对 Prometheus 不可见。

- 影响：观测面板看不到"有多少请求被鉴权拒掉"，安全事件排查缺数据。
- **决策（2026-08-16）：补计数已落地** — `auth_middleware` 两个 401 拒绝分支各自 `REQUEST_COUNT.labels(..., status_code="401").inc()`（复用同一指标，与 metrics 中间件的标签基数一致）。401 因在最外层直接返回、不会被 metrics 中间件计数，故拒绝分支自行计数。
  - 验证：`test_unauthorized_request_produces_401` 断言 `/metrics` 中出现 `path="/api/models",status_code="401"`。
